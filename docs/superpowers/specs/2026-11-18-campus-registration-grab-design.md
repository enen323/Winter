# 校园活动报名平台 —— 核心：名额抢报 设计文档

日期：2026-11-18
状态：待批准

## 1. 意图与为什么

做一个校园活动报名平台，业务范围是社团、讲座、竞赛、志愿活动的发布与报名。真正要打磨的是核心模块：**活动名额抢报** —— 名额有限、到点开放、瞬间大量用户同时抢。

做这件事的目的是**练高并发本身**，并且希望将来能用 STAR 法则把它讲清楚（S 场景 / T 任务 / A 手段 / R 结果）。这决定了项目的第一等公民不是功能数量，而是**可测量的证据**：压测脚本、监控、超卖校验、故障注入、优化前后对比。

长期希望真实上线给别人用，但本阶段的目标是把核心高并发模块做完、跑出可信数字、讲得清楚。上线所必需的业务脏活（学校统一身份、主办方审核、通知、签到）不在本阶段范围内。

## 2. 目标

1. **正确性**：任何并发与故障情况下，成功报名数 ≤ 名额数，且同一用户在同一活动只有一条有效报名记录（不超卖、不重复）。
2. **抗压**：开抢瞬间的单位时间洪峰不打穿系统；超出承载能力时明确拒绝（返回“已满/请稍后”），而不是拖垮服务。
3. **可测量**：一条命令起全栈、一条命令压测、一条命令校验正确性；每次压测产出结构化数据存档。
4. **可解释**：性能演进按阶梯推进，每一级都有 before/after 数据，能说明“哪个优化带来了多少提升”。
5. **最小业务闭环**：发布活动 → 查看活动 → 到点报名 → 查询报名结果 → 取消报名（名额回池）。

## 3. 非目标（本阶段明确不做）

- 微服务拆分、服务注册治理、K8s、分库分表、多机房容灾
- 学校统一身份认证（SSO）、支付、短信/邮件通知、签到核销
- 主办方审核流、活动内容富文本、图片上传与 CDN
- 移动端 App、精致前端（页面能点、能看结果即可，压测不依赖前端）
- 抽签/摇号模式（本阶段只做先到先得）

## 4. 反目标（技术上跑通也算失败）

- **出现超卖或重复报名**：无论 QPS 多好看，这是失败。
- **数字靠删业务换来的**：压测时不校验资格、不落库、不查重，只测 Redis 扣减。
- **不可复现**：压测要靠手工点一堆按钮或改代码才能跑，或结果无法在别人机器上重放。
- **只有峰值 QPS，没有正确性证明**：没有超卖校验脚本的压测结果不算结果。
- **优化痕迹丢失**：直接一步到位写最终架构，讲不出“从多少提升到多少、为什么”。

## 5. 约束

- 语言与框架：Java + Spring Boot（开发者主力栈）。
- 部署形态：单机 Docker Compose（MySQL、Redis、MQ、应用）。开发机基线：16 核 / 30GB 内存，压测与应用同机（数字口径在文档中如实标注，不宣称多机结论）。
- 中间件选取主流稳定版：MySQL 8、Redis 7、RocketMQ 或 RabbitMQ（实现时择一，以“削峰”为唯一诉求，不做选型炫技）。
- 压测工具：JMeter 为主（Java 生态、脚本可版本化），必要时用 wrk 交叉验证。
- 不在本阶段产生云主机等持续费用。

## 6. 考虑过的方案与取舍

**方案 A：单机一体化** —— 一个 Spring Boot 应用 + MySQL + Redis + MQ，全部在 Docker Compose 里，抢名额走 Redis 原子预扣 + MQ 异步落库。
换来：两三周就能跑出第一组数字，每层优化可独立压测对比；代价：讲不出分布式与服务治理的故事。

**方案 B：微服务形态** —— 网关 + 活动服务 + 报名服务 + 用户服务 + 注册中心 + 网关限流。
换来：更像生产系统；代价：工作量翻倍，大部分时间耗在联调与部署，核心并发逻辑没时间打磨；单机压测时多服务抢同一台机器 CPU，数字互相稀释，反而说不清哪个优化生效。

**方案 C：极简核心 + 极致证据** —— 一个服务、一个 Redis、一个 MySQL，把压测、监控、超卖校验、故障注入做到极致。
换来：R 最硬；代价：业务面薄，容易被评价为“秒杀 demo”。

**已选：A 为主线，吸收 C 的监控与故障注入，B 的网关限流与 MQ 削峰作为后续增量（加装前后各压一次，增量本身成为 A 的证据）。**

## 7. 核心设计

### 7.1 抢名额链路

```
用户 ──▶ Spring Boot 报名接口
            │
            ├─ 1. 资格与时间校验（活动存在、已到开抢时间、状态开放）—— 热点数据走缓存
            ├─ 2. Redis Lua 原子执行：库存>0 ? 未报名 ? 扣库存 : 记入已报名集合
            │      全部在一次性原子操作内完成，不依赖分布式锁
            ├─ 3. 返回结果码（成功 / 已满 / 已报名 / 未开始 / 无资格）
            └─ 4. 成功才发 MQ 消息 → 消费者落库（异步，不进用户等待路径）
```

**Redis 是名额判定的唯一权威点**，MySQL 是最终真相与审计，但不是判定点。

### 7.2 正确性防线（三层，任一层都无法单独造成超卖）

1. **Redis Lua 原子扣减**：`stock:{aid}` 与已报名集合 `enrolled:{aid}`（SET）在同一脚本内检查并修改，Redis 单线程串行化天然保证“先到先得”。
2. **MySQL 条件更新兜底**：落库时 `UPDATE activity SET stock = stock - 1 WHERE id = ? AND stock > 0`，影响行数为 0 则视为异常并按失败处理。
3. **MySQL 唯一索引**：`uk_activity_user (activity_id, user_id)`，物理上禁止同一用户在同一活动产生两条报名记录。

**幂等**：请求幂等键为 `(activityId, userId)`。Redis 集合天然去重；重试、重复提交、网络抖动重发均返回首次结果（结果缓存 `result:{aid}:{uid}` 保留一段时间，保证重试拿到同样的回答）。

**取消报名（名额回池）**：同样用 Lua 原子完成“移除集合成员 + 库存 +1”，仅允许已成功报名的用户取消；取消后写一条状态变更消息，DB 侧把记录置为 CANCELED 并回补库存，唯一索引保证重新报名不产生脏数据（改为复用同一条记录或使用部分唯一索引语义，实现时确定并在文档外记录）。

**失败补偿**：Redis 扣减成功但落库失败（MQ 丢失、消费异常、DB 不可用）时，由定时对账任务比对 Redis 已报名集合与 DB 记录，补偿落库或回滚库存，并输出对账差异指标。

### 7.3 抗压与削峰

- 用户等待路径只包含：校验 + 一次 Redis 原子操作 + 一次发送消息（失败降级为本地失败队列重试），不包含 DB 写入。
- MQ 消费端按活动分批落库，控制写入速率，避免瞬时洪峰把 MySQL 打死。
- 网关/接口层令牌桶限流 + 单用户滑动窗口频控（每人每活动每秒 N 次），超出直接返回“请求过于频繁”，保护后端。
- 活动详情为典型热点 key：本地缓存（Caffeine，秒级过期）+ Redis，防穿透用空值缓存、防击穿用逻辑过期/单飞、防雪崩用随机过期时间。

### 7.4 数据模型（初版）

- `activity(id, title, capacity, stock, start_time, status, version)`
- `registration(id, activity_id, user_id, status, created_at, updated_at)` + `uk_activity_user`
- Redis：`stock:{aid}`、`enrolled:{aid}`(SET)、`result:{aid}:{uid}`

### 7.5 性能演进阶梯（每级都留档）

| 级别 | 做法 | 记录内容 |
|------|------|----------|
| L0 | 直连 MySQL 条件更新扣库存 | QPS / P99 / 超卖数（基线） |
| L1 | Redis Lua 预扣 + 同步落库 | 同上 + Redis 命中率 |
| L2 | + MQ 异步落库 | 同上 + MQ 堆积/消费延迟 |
| L3 | + 活动详情多级缓存 | 同上 + 缓存命中率 |
| L4 | + 限流与频控 | 同上 + 被限流比例、错误码分布 |
| L5 | + 结果查询走 Redis（轮询不打 DB） | 同上 |

## 8. 证据链（STAR 里 R 的来源）

- **压测**：脚本入库，参数（并发数、持续时长、目标活动名额）可配置，一条命令复跑；每轮产出 `docs/benchmarks/YYYY-MM-DD-Lx-<说明>.md`，含配置、原始结果、结论。
- **指标**：QPS、P50/P99/P999 延迟、错误率、CPU/内存、Redis 命中率、MQ 堆积量。Prometheus + Grafana（Spring Actuator + Micrometer）。
- **正确性校验**：压测后自动断言 `DB 成功报名数 == 名额上限` 且 `无重复 (activity_id,user_id)` 且 `Redis 库存 == 0`；校验脚本随压测一起跑。
- **故障注入**：至少覆盖 ①压测中杀 Redis（验证降级与不超卖）②停 MQ 一段时间后恢复（验证不丢单、对账生效）③MySQL 注入延迟（验证用户路径不被拖垮）。每个场景记录现象与结论。
- **优化对比**：阶梯表中每一级的前后数据，即优化的 A 与 R。

## 9. 附加高并发小模块（复用同一底座，各 1–2 天）

1. **热点活动详情缓存**（穿透/击穿/雪崩三件套，含本地缓存一致性处理）。
2. **防刷与限流**（令牌桶 + 滑动窗口频控 + 统一限流响应）。

第三个可选：**候补队列**（名额释放时按队列顺序补位，MQ 延迟消息 + 通知）。

## 10. 验收标准（Definition of Done）

- 一条命令起全栈、一条命令跑压测、一条命令跑正确性校验。
- 至少 3 组阶梯数据（L0 / L2 / L4），每组含 QPS、P99、错误率、超卖数=0。
- 至少 2 个故障注入场景有记录与结论。
- 能不看文档口述 3 分钟完整 STAR。

## 11. 留给实现者的部分

- 具体依赖版本号、包结构、表字段类型与索引细节。
- MQ 产品最终选型（RocketMQ / RabbitMQ）与消息格式、重试与死信策略。
- 压测参数取值（并发梯度、时长）、限流阈值初值（由 L0 数据反推）。
- 取消后重新报名的记录语义（复用记录 vs 部分唯一索引）的具体实现。
- 前端页面形态（Thymeleaf 服务端渲染或极简 Vue 页面）。
