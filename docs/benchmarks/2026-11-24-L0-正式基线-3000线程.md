## 三、结果

| 指标 | 值 |
| --- | --- |
| **吞吐 Throughput** | **600.5 /sec** |
| **Error %** | **83%** |
| 平均 / P50 / P90 / P95 / P99 / Max | **2922 / 3158 / 3878 / 4143 / 4581 / 4783 ms** |
| 墙钟 | **5.00 秒**（由 `.jtl` 算出；`3000 ÷ 5.00 = 600.5`，与 JMeter 报的完全一致） |
| 样本数 | 3000（`success=true` 500 + `success=false` 2500） |
| HTTP 状态码 | 3000 个全是 `200` |

延迟分位数是从 `run.jtl` 现算的，不是估的。

### 按成败拆开的延迟（这张表比总表有用）

| 分组 | n | 平均 | P50 | P90 | P95 | P99 | Max |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 报名成功 | 500 | **1328** | 1456 | 1976 | 2317 | 2681 | 2733 ms |
| 被拒绝 | 2500 | **3241** | 3246 | 3949 | 4214 | 4605 | 4783 ms |

**成功的比被拒的快 2.4 倍。** 这不是反常：被拒的 2500 个请求排在成功者后面等锁，等的是「前面所有人都放锁」；成功的 500 个里最早的那批几乎不用等。

对照 1000 线程那轮（成功 541 ms / 被拒 1150 ms）：线程数 ×3，两组延迟都 ×2.4——是排队变长，不是单次变慢。

### Error % = 83% 的正确解释

**这不是错误率，是拒绝率。** 3000 个线程抢 500 个名额，2500 个被拒，2500 ÷ 3000 = 83.3%。

HTTP 契约是「业务失败也回 HTTP 200，成败看 body 的 code」，所以 JMeter 看到的 3000 个请求全是 `200 OK`；标红的是 **Response Assertion**（只匹配 `"code":0`），它把 `code:1001` 判成了失败。

**本项目里 Error % 永远等于拒绝率**，基础设施真挂了才会出现 HTTP 500。

### 业务码分布

| code | 含义 | 数量 | 依据 |
| --- | --- | --- | --- |
| 0 | 报名成功 | **500** | ✅ `verify.sh` 断言 ① 直接确认（DB `CONFIRMED` = 500） |
| 1001 | 名额已满 | **2500** | 3000 − 500，减法得出 |
| 1002 | 已报名过 | 0 | 账号池 3000 个不重复，且每人只发一个请求 |
| 1003 | 未到开抢时间 | 0 | 见下方说明 |
| 1004 | 已关闭 | 0 | 活动状态为 OPEN |

**为什么 `1003` 可以确定是 0**：如果 `start_time` 被设成未来，3000 个请求会**全部**返回 `1003`、成功数为 0。而 `verify.sh` 确认成功数正好 500，说明开抢时间已过——不存在「一部分 1003 一部分 1001」还能凑出 500 的场景（真有 1003 的话，那些线程根本没进到报名逻辑）。

**`success=true` 正好 500 个，与 `verify.sh` 的 500 互相独立地对上了**——一个来自 JMeter 的响应断言，一个来自 MySQL 的 `COUNT(*)`，两条路径同一个数。这是本轮最结实的一个交叉验证。

**还没被直接测到的**：2500 个拒绝的内部构成（是否全是 `1001`）没有 `.jtl` 的 `bizCode` 列佐证。上面的结论是从「成功数 = 500」反推的，逻辑上站得住，但属于推断而非实测。

> **下一轮怎么补上这一列**：`bizCode` 是 JSONPostProcessor 提取的 JMeter 变量，**默认不写进 `.jtl`**。必须在命令行加 `-Jsample_variables=bizCode`：
>
> ```bash
> jmeter -n -t jmeter/grab.jmx -Jthreads=3000 -JactivityId=1 -Jjtl=run.jtl -Jsample_variables=bizCode
> ```
>
> 已实测：加了它，表头多出最后一列 `"bizCode"`，`awk -F, '{c[$NF]++}' run.jtl` 直接出分布。
> **它不是 JMX 里的设置**——`SampleEvent.initSampleVariables()` 读的是 `JMeterUtils.getProperty("sample_variables")`，即 JMeter 属性；往 ResultCollector 里塞 `<stringProp name="sample_variables">` 是无效的（试过，列不出现）。

## 五、结论

### 5.1 两轮数据刚好能被一个两参数模型解释

把两轮放一起：

| 轮次 | 线程数 | 成功数 | 被拒数 | 吞吐 | 墙钟 |
| --- | --- | --- | --- | --- | --- |
| 试跑 | 1000 | 500 | 500 | 314.2 /sec | 3.18 s |
| 本轮 | 3000 | 500 | 2500 | 600.5 /sec | 5.00 s |

设「每个成功报名占锁 `a` 毫秒、每个被拒请求占锁 `b` 毫秒」：

```text
500a + 500b  = 3183 ms      （试跑轮）
500a + 2500b = 4996 ms      （本轮）
相减：2000b = 1813 ms  →  b ≈ 0.9 ms
代回：500a = 2733 ms   →  a ≈ 5.5 ms
```

也就是说：**一个成功报名要在行锁里花约 5.5 ms（INSERT + UPDATE + COMMIT），一个被拒请求也要约 0.9 ms（拿锁、看 `stock<=0`、抛异常回滚）。** 两个数据点被这个模型同时解释，误差在取整范围内。

### 5.2 因此要修正上一轮基线里的一个结论

`2026-11-23-L0-基线.md` 写的是「L0 吞吐 ≈ `1 / 单事务耗时`，跟 16 核基本无关——加机器没用」。**这句话说过头了。**

本轮 3 倍线程换来 1.9 倍吞吐，说明被拒请求的锁持有时间虽短但不可忽略，线程数确实还能榨出一些吞吐。按上面的模型，L0 的吞吐上限是：

```text
全部成功：1 / 5.5ms  ≈ 182 次成功报名/sec
全部被拒：1 / 0.9ms  ≈ 1111 次/sec
```

两个上限都远低于 D4 定的 5000+ QPS 目标——**L0 撑不到目标是结论，但「加机器完全没用」不是**。

### 5.3 这给 L1 指出了明确的优化点

被拒的 2500 个请求在 L0 里也要走一遍数据库：拿行锁、读 stock、发现 `<=0`、抛异常、回滚。L1 把这一步搬到 Redis Lua 里，被拒请求根本碰不到 MySQL——按模型，这 2500 × 0.9ms = 2.25 秒的锁时间直接消失，剩下的 500 × 5.5ms = 2.75 秒才是真下限。

**这个推算给 L1 留了一个可证伪的预期**：如果 L1 的吞吐没有明显超过 `500 / 2.75s ≈ 182/sec` 的成功报名能力，说明异步落库没把成功路径变短，L1 的优化就只体现在拒绝路径上。

### 5.4 还没被证明的事

- 2500 个拒绝的内部构成未经 `.jtl` 的 `bizCode` 列直接确认（见第三节，下一轮加 `-Jsample_variables=bizCode`）
- 行锁等待增量的具体值没抄下来（见第四节）
- 没记录 CPU / 内存 / MySQL 连接数，无法判断 5.5ms 是花在 CPU 还是在等 IO
- 应用与 JMeter 同机，5.5ms 里有多少是抢 CPU 抢出来的，说不清
- 当前 DB 状态已脏（`id=1` 的 `status='501'`），`verify.sh check 1 500` 现在会 FAIL
