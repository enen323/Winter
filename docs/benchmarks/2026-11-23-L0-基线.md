## 三、结果

| 指标 | 值 |
| --- | --- |
| **吞吐 Throughput** | **314.2 /sec** |
| **Error %** | **50%** |
| 平均 / P50 / P90 / P99 / Max | 待补（GUI 跑的没存 `.jtl`，下次开 Simple Data Writer） |

### Error % = 50% 的正确解释

**这不是错误率，是拒绝率。** 1000 个线程抢 500 个名额，一半抢到一半被拒。

HTTP 契约是「业务失败也回 HTTP 200，成败看 body 的 code」，所以 JMeter 看到的 1000 个请求全是 `200 OK`；标红的是 **Response Assertion**（只匹配 `"code":0`），它把 500 个 `code:1001` 判成了失败。

**本项目里 Error % 永远等于拒绝率**，基础设施真挂了才会出现 HTTP 500。

### 业务码分布（比 JMeter 的 Error % 准确）

| code | 含义 | 数量 |
| --- | --- | --- |
| 0 | 报名成功 | **500** |
| 1001 | 名额已满 | **500** |
| 1002 | 已报名过 | 0 |
| 1003 | 未到开抢时间 | 0 ← 说明 `start_time` 设成了过去，没踩坑 |
| 1004 | 已关闭 | 0 |

`1003 = 0` 很重要：如果 `start_time` 设成未来，这里会是 500，整轮数据作废。

## 四、正确性校验（`bin/verify.sh check 1 500`）

```text
PASS ① DB CONFIRMED = 500
PASS ② 无重复 (activity_id, user_id)
PASS ③ DB stock = 0
PASS ④ 死锁增量 = 0
     行锁等待增量 = 999（这些请求真的在同一条行锁上排过队）
```text

| 断言 | 结果 |
| --- | --- |
| DB `CONFIRMED` 数 == capacity | 500 == 500 ✅ 不多不少，**没超卖也没吞名额** |
| 无重复 `(activity_id, user_id)` | ✅ 唯一索引真的建了 |
| DB `stock` == 0 | ✅ |
| 死锁增量 | **0**（上一轮的死锁修复确实生效） |
| Redis `stock` / `enrolled` | L0 不涉及 |

数据库实测状态：`activity id=1, capacity=500, stock=0`；`registration` 表 `CONFIRMED` 500 行。

## 五、结论

L0 把 500 个名额原样卖出去了，一个不多一个不少，死锁 0。**这是合格的对照组。**

**瓶颈形态已经被数据说清楚**：行锁等待增量 999 ≈ 样本数 1000，说明**每一个**请求（无论成功还是被拒）都排在同一个 activity 行的锁上。500 个成功的在锁里做 INSERT + UPDATE + COMMIT，500 个被拒的也要拿锁、看 `stock<=0`、抛异常回滚。

所以 L0 的吞吐 ≈ `1 / 单事务耗时`，跟 16 核基本无关——加机器没用，这是 L0 存在的意义。
