# 数据异常：`registration` 出现 `status='501'`

- **发现时间**：2026-11-24 10:30（L0 基线复查）
- **影响**：`bin/verify.sh check 1 500` 现在 FAIL（`DB 报名成功数 = 499，期望 500`）
- **状态**：**已查清，作者手工制造，verify.sh 行为正确**

## 事实

```sql
SELECT id, activity_id, user_id, status, HEX(status), created_at, updated_at
FROM registration WHERE id = 1;
```

| 字段 | 值 |
| --- | --- |
| id | 1 |
| activity_id | 1 |
| user_id | 15 |
| status | `501`（`HEX(status)` = `353031`，即 ASCII `501`，长度 3） |
| created_at | 2026-11-24 10:14:31.193 |
| updated_at | 2026-11-24 10:24:51.236 |

同表其余 499 行：`status='CONFIRMED'`，`id` 2–500，`created_at` 10:14:31–10:14:34。`stock=0`、`capacity=500`。

## 已排除的解释

**应用代码不可能写出 `'501'`。** 全仓库搜过所有写 `registration.status` 的地方：

- `RegistrationMapper.java:17` — `INSERT INTO registration (activity_id, user_id, status) VALUES (#{activityId}, #{userId}, 'CONFIRMED')`，字面量硬编码
- `Registration.java:53` — `setStatus(RegistrationStatus status)`，枚举只有 `CONFIRMED` / `CANCELED`
- L0 阶段**没有任何 UPDATE registration 的语句**（`reuseRow` 属于 L1.5，未实现）

所以 `'501'` 只能是外部写入的。`501` 本身是 HTTP `Not Implemented`，与业务码表（`ResultCode` 里没有 501）对不上。

**binlog 可回溯但读不了**：`log_bin=ON`，`/var/lib/mysql/binlog.000023`（864KB，覆盖该时段），但文件 root 所有，本会话 `sudo` 无 TTY。需要作者执行：

```bash
sudo mysqlbinlog --base64-output=DECODE-ROWS -v /var/lib/mysql/binlog.000023 \
  | grep -i -B2 -A2 "registration"
```

`general_log` 是 OFF，帮不上。

## 结论：作者手工制造的测试，`verify.sh` 没有看错

作者确认（2026-11-24 10:32）：「我动过，刚刚用来测试 verify check 会不会失败，验证出来这个 verify check 没有问题」。

也就是说这一行是**故意**造出来喂给断言 ① 的，而断言 ① 当场就抓住了它：

```text
$ bin/verify.sh check 1 500
VERIFY FAILED: DB 报名成功数 = 499，期望 500（名额被吞或超卖）
```

**结论：断言 ① 是活的。** 一个从没失败过的校验脚本，它的通过没有意义——现在它有真实的失败记录了，后面 L1/L2 的「五条断言全过」才有分量。

## 已清理

`bin/verify.sh reset` 已执行，`registration` 与 `activity` 清空、id 从 1 重新开始。
基线记录（`2026-11-24-L0-正式基线-3000线程.md`）作为当时快照仍然有效。

## 顺带查清的两件事

### 1. 断言 ④ 的死锁计数器是活的，不是永远 0 的摆设

```sql
SELECT NAME, STATUS, COUNT FROM information_schema.INNODB_METRICS WHERE NAME='lock_deadlocks';
-- lock_deadlocks | enabled | 0
```

`STATUS=enabled`，不是 `disabled`——`disabled` 的计数器恒返回 0，那样断言 ④ 就永远是空过的。已确认不是这种情况。

### 2. 这台 Redis 上还有作者其他项目的 key，`reset` 绝不能 FLUSHDB

2026-11-24 实测 882 个 key，形如 `$sales$DATA_DICT_*`、`20$sales$...`，是 CRM/销售系统的数据字典缓存。本项目 L0 阶段一个 key 都没有（符合预期）。

计划第 548 行原本就写着「`bin/verify.sh reset` 清 DB 与 Redis」，但实现只清了 DB——**这是个会炸 L1 的坑**：L1 起 `stock:1` 不清掉，下一轮新活动建好也会被 Lua 当成「名额已满」，而现象是「所有人都报名失败」，很难往回追。

已修：`cmd_reset` 增加 `redis_reset_keys()`，用 `SCAN` + `MATCH` 只删本项目五个前缀（`stock:` / `enrolled:` / `result:` / `activity:` / `barrier:`），并留了一个 canary key `$sales$DATA_DICT_CANARY` 验证别人的数据不受影响（实测 888 → 883，删掉 5 个我们的，canary 原样留着）。
