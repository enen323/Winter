# 压测会怎么骗人 —— 两个「坏」jmx 的实测记录

**日期**：2026-11-24
**级别**：Stage P（压测脚手架）
**应用**：L0 直连 MySQL 条件更新，`--spring.profiles.active=l0`
**作者跑的部分**：`jmeter/grab-broken-same-user.jmx`、`jmeter/grab-broken-no-assertion.jmx`，GUI

这份文件不是某一级的性能基线，是**证明「压测数字本身不证明任何东西」的两个实验**。
基线数据在 `2026-11-24-L0-正式基线-3000线程.md`，这份只讲仪器会怎么撒谎。

---

## 实验 A：所有人用同一个身份

`jmeter/grab-broken-same-user.jmx`

**怎么造的**：`setUp 线程组` 先注册固定账号 `broken_same_user`，主线程组每个线程先 `POST /api/auth/login` 拿这个账号的 token，再用它报名。CSV 与 SyncTimer 禁用（只有一个身份，没有并发可造）。

报名接口从 JWT token 解 userId，**根本不看 body 也不看 CSV**——所以「CSV 改成常量 userId」是无效的，必须让所有线程真的拿到同一个身份的 token。

### 作者 GUI 跑的结果（100 线程）

| 指标 | 值 |
| --- | --- | --- |
| 样本 | 200（100 登录 + 100 报名） |
| 报名成功 | **1** |
| 报名被拒 | **99** |
| Err | 99% |

### 我补跑的完整数据（1000 线程，非 GUI，打开 `bizCode` 记录）

| 指标 | 值 |
| --- | --- | --- |
| 报名样本 | 1000 |
| `code=0` 报名成功 | **1** |
| `code=1002` 已报名过 | **999** |
| 报名吞吐 | 135 /s |

**它证明了什么**：这不是并发缺陷，是**仪器测错了东西**。
1000 个请求看起来在抢名额，实际上第一个成功后其余 999 个全撞在
`uk_activity_user` 唯一索引上返回 `1002`。你看到的吞吐、延迟、成功率全是
**去重逻辑**的性能，不是抢名额的性能。

**为什么危险**：如果只报「QPS 135、成功率 0.1%」，会得出「系统扛不住并发」的错误结论；
如果只看那 1 个成功，会以为一切正常。两个方向都错。
**面试里唯一别人答不上的就是这一条**——大多数人只会在报告里写吞吐量。

## 实验 B：去掉响应断言

`jmeter/grab-broken-no-assertion.jmx`

**怎么造的**：与 `grab.jmx` 只差一处本质——「响应体含 code:0」的 ResponseAssertion 被
**禁用**（右键 → Enable 即可打开）。JSONPostProcessor 故意保留。

### 作者 GUI 跑的结果（1000 线程）

| 指标 | 值 |
| --- | --- | --- |
| 样本 | 1000 |
| HTTP 200 | 1000 |
| **Err** | **0.00%** |
| success=true | **1000 / 1000** |

屏幕一片绿，零错误，吞吐 2500/s（墙钟 0.40 s）。

### 我补跑的完整数据（1000 线程，非 GUI，打开 `bizCode` 记录）

| 指标 | JMeter 看到的 | 实际发生的 |
| --- | --- | --- |
| HTTP 200 | 1000 | 1000 |
| **Err** | **0.00%** | —— |
| success=true | **1000 / 1000** | —— |
| `code=0` 报名成功 | 看不到 | **500** |
| `code=1001` 名额已满 | 看不到 | **500** |
| 吞吐 | 277 /s | —— |
| DB 真相 | 看不到 | `registration` 500 行、`stock = 0` |

**它证明了什么**：**Error % 在本项目恒等于拒绝率，不是错误率。**
HTTP 契约是「业务失败也回 HTTP 200，成败看 body 的 code」，所以 JMeter 看到 1000 个
请求全是 `200 OK`；标红的本来是 ResponseAssertion 匹配 `\"code\":0` 的结果。
去掉断言后，2500 个被拒请求（3000 线程那轮）全部算成成功。

如果只看这一屏就写报告，会得出「1000 人全部报名成功」——**超卖 500 个名额**。
必须回到 DB 才看得见真相：`SELECT COUNT(*) FROM registration WHERE status='CONFIRMED'` = 500。

这就是 `bin/verify.sh check` 存在的全部理由，也是为什么 Stage P Step 6
（「证明 verify.sh 会失败」）必须做——**一个从没失败过的校验脚本，它的通过没有意义**。

## 意外插曲：token 过期会让屏幕更绿

补跑实验 B 时第一轮全部样本 `bizCode=1400`（未登录/token 无效），而 JMeter 依然报
**Err: 0.00%、success=true 1000/1000、1848/s**。

原因：`jmeter/tokens.csv` 是 10:07 生成的，而 `winter.jwt.ttl = PT30M`，
10:37 起全部失效。1000 个请求连 `JwtAuthFilter` 都没过，报名逻辑一次都没执行。

**这是实验 B 的更极端版本**：去掉响应断言后，连「用户根本没登录」都看不出来。
所以每轮压测前必须重新 `bin/seed-users.py <count>`，并且要在报告里写错误码分布，
不能只写错误率。

## GUI 下怎么看业务码分布

三个 jmx 里都加了一个 `JSR223PostProcessor`，名字叫「把业务码追加到样本名」：

```groovy
def code = vars.get("bizCode")
if (code != null) {
    prev.setSampleLabel(prev.getSampleLabel() + " code=" + code)
}
```

它排在 JSONPostProcessor（提 `bizCode`）之后，把 code 拼到样本名上。于是：

- **GUI**：Aggregate Report / Summary Report 直接按 code 分行——`POST 报名 code=0` 500 行、`POST 报名 code=1001` 500 行。这就是错误码分布，零额外配置
- **.jtl**：code 落在 `label` 列（表头里本来就有），`awk -F, '{print $3}'` 和 `csv.DictReader` 都能正确解析

实测确认（1000 线程）：

| jmx | Aggregate Report 分组 |
| --- | --- |
| `grab-broken-no-assertion.jmx` | `code=0` 500 / `code=1001` 500，**Err 仍 0.00%** |
| `grab-broken-same-user.jmx` | `code=0` 1 / `code=1002` 999，Err 49.93% |

`grab-broken-same-user.jmx` 的响应断言**仍然生效**（Err 999 就是它报的）——追加 label 不影响断言匹配响应体。

### 为什么不用 `sample_variables`

那是 **JMeter 属性**，只能在启动时给（`-Jsample_variables=bizCode` 或写进 `jmeter.properties`）。
`SampleEvent` 在**类加载时**读一次就缓存了：

```java
private static volatile String[] variableNames;   // SampleEvent
static { ... initSampleVariables(); }              // <clinit>，跑测试计划之前就执行完
```

实测在 setUp 线程组里 `props.put("sample_variables", "bizCode")` + `SampleEvent.initSampleVariables()`
（这方法是 `public static`，所以调得动）能把值写进行里，但表头在 `testStarted()` 就写好了，
结果是 **17 列数据配 16 列表头的畸形 CSV**。

## 三个实验合起来的结论

| 实验 | 屏幕显示 | 实际 |
| --- | --- | --- |
| 正常（`grab.jmx`） | Err 83%、QPS 600 | 500 成功 + 2500 被拒，DB 500 行 |
| 实验 A 同一身份 | 成功率 0.1% | 在测去重，不在测抢名额 |
| 实验 B 无断言 | **Err 0.00%、全绿** | 500 成功 + 500 被拒 |
| 实验 B 加 token 过期 | **Err 0.00%、1848/s** | **一个请求都没进报名逻辑** |

**压测数字本身不证明任何东西。** 证明它的是你同时看到的三样东西：

1. `bin/verify.sh check` 的五条断言（服务端真相）
2. 错误码分布（`code=0` / `1001` / `1002` / `1003` / `1400` 各多少），不是笼统错误率
3. 成功数与活动名额对得上

少任何一样，数字就只是「接口返回 200 有多快」。

## 怎么复现

```bash
# 1. 起应用（L0）后，每轮都要重新生成账号池——token 30 分钟过期
bin/seed-users.py 1000 http://localhost:8081

# 2. 复位 + 灌活动（startTime 必须是过去，否则全 code=1003 整轮作废）
bin/verify.sh reset
FUTURE=$(python3 -c 'import datetime;print((datetime.datetime.now()-datetime.timedelta(hours=1)).strftime("%Y-%m-%dT%H:%M:%S"))')
curl -X POST http://localhost:8081/api/activities \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d "{\"title\":\"实验\",\"capacity\":500,\"startTime\":\"$FUTURE\"}"

# 3. 跑（-Jsample_variables=bizCode 让 .jtl 多出最后一列 bizCode，直接 awk 出分布）
jmeter -n -t jmeter/grab-broken-no-assertion.jmx -Jthreads=1000 -Jsample_variables=bizCode -l run.jtl
awk -F, '{c[$NF]++} END{for(k in c) print k, c[k]}' run.jtl

# 4. 对真相
bin/verify.sh check 1 500
```

`bizCode` 那一列**只能**用 JMeter 属性打开（`-Jsample_variables=bizCode`）。
往 ResultCollector 里塞 `<stringProp name="sample_variables">bizCode</stringProp>` 是无效的——
`SampleEvent.initSampleVariables()` 读的是 JMeter 属性，不是 JMX 元素设置。

**注意**：`-l run.jtl` 用同一个文件名重复跑会被**追加**且不重写表头，
第二轮起解析脚本会把两轮数据混在一起。每轮换个文件名。
